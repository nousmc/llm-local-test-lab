Questo e' il campo piu' importante del test case. Definisce COSA il modello deve produrre e COME viene valutato.
Deve essere un JSON valido. I campi principali, che variano per tipo test:

Per TUTTI i tipi:
schema — la struttura JSON attesa (es. {"label":"string"}, {"invoice_number":"string","total":"number"}). Obbligatorio. Usato per validare che l'output abbia i tipi corretti.
expected — i valori ground-truth attesi (es. {"label":"network_issue"}, {"total":1280.40}). Confrontati campo per campo con l'output del modello.
required_fields — lista dei campi obbligatori. Se mancano → penalita'.
allowed_labels — classi ammesse per classificazione (es. ["helpdesk","network_issue","billing"]).

Specifici per tipo: RAG: answer_facts, must_cite_context, answer_absent. Sintesi: required_points, max_words. Code analysis: expected_findings (con type/severity/description). Refactoring: constraints, target. Code doc: must_include, expected_parameters. Image desc: required_objects, max_words. Speech-to-text: action_items, clean_transcript_contains. Contextual insight: must_include_themes, must_avoid_themes.

Esempio classification: {"schema":{"label":"string"},"expected":{"label":"network_issue"},"required_fields":["label"],"allowed_labels":["helpdesk_password_reset","network_issue","billing","other"]}
Esempio data_extraction: {"schema":{"invoice_number":"string","date":"date","total":"number"},"expected":{"invoice_number":"42","date":"2026-04-15","total":1280.40},"required_fields":["invoice_number","date","total"]}
Esempio RAG: {"answer_facts":["26 giorni di ferie","Richiedere sul portale HR"],"must_cite_context":true,"answer_absent":false}
Testo libero atteso (non JSON). Usato solo per tipi NON strutturati (RAG, sintesi, code analysis, refactoring, image desc, contextual insight). Per tipi strutturati (classification, data_extraction, OCR) viene ignorato. Serve come fallback per il validator LLM se expected_output_json e' vuoto, e per metriche lessicali (exact_match, Jaccard). Popolare expected_output_json e' preferibile e piu' preciso.
Vecchio formato etichette (es. {"correct_label":"billing"}). Preferire expected_output_json che contiene anche schema e required_fields. Questo campo e' mantenuto per retrocompatibilita' con test legacy.
Guida per il validator LLM, NON per lo scoring deterministico. Criteri di valutazione aggiuntivi passati al modello giudice. Esempio: {"field_match_weight":0.6,"schema_compliance_weight":0.4}. Il validator usa questa rubrica per assegnare semantic_score e format_score. Non influisce sulle metriche deterministiche (Jaccard, field_accuracy, exact_match) che usano solo expected_output_json.
Etichette di categorizzazione. Esempio: ["classification","helpdesk","IT"]. Usate per filtro e analisi.
Livello di difficolta' del test. Usato per analisi comparative e filtri.
